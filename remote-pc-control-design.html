동의 기반 Windows 원격 제어 프로그램 설계

대상자가 프로그램을 설치하고 명시적으로 허가할 때에만 원격 접속이 가능한, 릴레이 서버 경유 · WebRTC 기반의 트러블슈팅용 원격 제어 도구. 구현 언어는 C#(.NET)을 1순위, Golang을 대안으로 상정한다.

플랫폼 Windows 10/11 x64 전송 WebRTC (DTLS-SRTP) 연결 Relay(TURN) 경유 언어 C# · Go(대안) 모델 Opt-in 동의
01

개요와 범위

목표는 원격지 PC에서 발생한 문제를 지원자가 직접 화면을 보고 조작하며 해결하도록 돕는 도구를 만드는 것이다. 핵심 제약은 대상자 동의 없이는 어떠한 접속도 성립하지 않는다는 점이다. 접속은 대상자가 프로그램을 설치하고 세션을 열어 코드를 공유하며, 조작 시작 직전 동의 대화상자에서 명시적으로 허용해야 시작된다.

포함 범위 (In Scope)

  • 실시간 화면 공유 — 대상 PC의 화면을 지원자에게 저지연으로 스트리밍한다.
  • 원격 마우스·키보드 제어 — 지원자의 입력을 대상 PC에 주입한다.
  • 파일 전송 — 로그 수집, 패치 전달을 위한 양방향 파일 송수신을 제공한다.
  • 텍스트 채팅과 시스템 정보 조회 — 트러블슈팅 보조 채널을 제공한다.
  • 세션 단위 동의와 가시적 표시 — 접속 중임을 대상자가 항상 인지하도록 한다.

제외 범위 (Out of Scope, 초기 버전)

  • 무인(Unattended) 상시 접속 — 별도 보안 설계가 필요하므로 초기에는 유인 세션만 다룬다.
  • macOS·Linux 지원 — Windows 전용으로 한정한다.
  • 다자 동시 접속·회의 — 1:1 지원 세션에 집중한다.
설계 원칙

대상자 통제권 우선, 최소 권한, 전 구간 암호화, 감사 로그. 이 네 가지가 모든 기능 결정에 우선한다. 편의 기능이 이 원칙과 충돌하면 원칙을 따른다.

02

전체 아키텍처

시스템은 세 개의 독립 구성요소로 나뉜다. 대상 PC에서 도는 Host Agent, 지원자가 사용하는 Viewer, 그리고 둘을 이어주는 Signaling + Relay 서버이다. 실제 화면·입력 데이터는 서버를 최소한으로만 거치도록 WebRTC로 직접 채널을 맺고, 서버는 연결 중개(시그널링)와 NAT 통과 보조(STUN/TURN)를 담당한다.

구성요소 역할

Host Agent

대상 PC 에이전트

설치형 네이티브 앱. 화면을 캡처·인코딩해 송출하고, 수신한 입력 이벤트를 OS에 주입한다. 동의 대화상자와 세션 표시를 책임진다.

Viewer

지원자 클라이언트

웹 브라우저(설치 불필요) 또는 데스크톱 앱. 화면을 그리고 마우스·키보드 입력을 캡처해 데이터 채널로 보낸다.

Server

시그널링·릴레이

세션 코드 발급, 두 피어의 SDP·ICE 후보 교환, NAT 통과용 STUN/TURN 제공. 미디어 원본은 저장하지 않는다.

왜 WebRTC인가

DTLS-SRTP 종단 암호화, 표준 NAT 통과(ICE/STUN/TURN), 적응형 비트레이트, 저지연 미디어 채널 + 신뢰성 있는 데이터 채널을 표준으로 제공한다. 릴레이 경유 요구사항과 방화벽 환경을 고려할 때 직접 프로토콜을 짜는 것보다 리스크가 낮다.

03

04

연결·시그널링 흐름

두 피어는 서로의 주소를 모른 채 시작한다. 서버는 세션 코드를 매개로 둘을 같은 룸에 묶고, WebRTC 협상에 필요한 SDP와 ICE 후보만 오가게 한다. 협상이 끝나면 미디어·데이터는 가능한 한 서버를 거치지 않고 직접 흐른다.

Host (대상)
Server
Viewer (지원자)
1

세션 생성

대상자가 Host 앱에서 "세션 시작"을 누르면 서버에 룸을 만들고 일회성 세션 코드(예: 9자리 + PIN)를 발급받아 화면에 표시한다.

Host → Server: createSession()
2

코드 공유

대상자가 세션 코드를 지원자에게 전화·메신저로 전달한다. 코드는 대역 외(out-of-band)로 전달되어 무작위 접속을 차단한다.

Server: 룸 대기, 코드-룸 매핑 보관
3

세션 참가

지원자가 Viewer에서 코드와 PIN을 입력한다. 서버가 검증 후 두 피어를 같은 룸에 연결하고 시그널링 채널을 연다.

Viewer → Server: join(code, pin)
4

Offer / Answer 교환

Host가 SDP Offer를, Viewer가 Answer를 생성해 서버를 통해 교환한다. 미디어 트랙(화면)과 데이터 채널(입력·파일·채팅)을 이때 정의한다.

Host ⇄ Server ⇄ Viewer: SDP
5

ICE 후보 수집·교환

양측이 STUN으로 공인 IP 후보를, 필요 시 TURN 릴레이 후보를 모아 교환한다. 최적 경로(P2P 우선, 실패 시 릴레이)를 자동 선택한다.

STUN/TURN ↔ 양 피어
6

동의 확인

연결 직전 Host가 동의 대화상자를 띄운다. 대상자가 "허용"을 눌러야만 화면 트랙과 입력 채널이 활성화된다. 거부 시 세션은 종료된다.

Host: consent gate
7

P2P 연결 성립·스트리밍

DTLS 핸드셰이크로 종단 암호화가 서고, 화면 스트림과 입력 데이터 채널이 흐른다. 서버는 이후 미디어에 관여하지 않는다(릴레이 폴백 제외).

Host ⇄ Viewer: SRTP + DataChannel
05

화면 캡처와 인코딩

화면 캡처는 두 가지 Windows API를 상황에 따라 쓴다. 최신 방식인 Windows Graphics Capture(WGC)를 기본으로, 하위 호환·저지연이 필요한 경우 DXGI Desktop Duplication을 폴백으로 둔다.

방식장점제약권장 용도

(Win10 1803+)		모니터·창 단위 캡처, 커서 포함, HDR·최신 안정성, WinRT로 접근 쉬움캡처 대상 테두리 표시(정책), UWP 상호운용 필요기본 일반 데스크톱

파이프라인

캡처된 GPU 프레임은 가능하면 CPU로 내리지 않고 하드웨어 인코더로 직접 넘긴다. 코덱은 하드웨어 가속이 가장 폭넓은 H.264를 기본, 라이선스·호환을 고려한 VP8을 대안으로 둔다.

// 화면 송출 파이프라인 (Host)
Capture(WGC/DXGI) → GPU Frame
    → Encode(H.264 HW via Media Foundation / VP8)
    → Packetize(RTP) → WebRTC MediaTrack
    → (P2P 또는 TURN) → Viewer decode → render
  • 적응형 품질 — 대역폭·왕복지연에 따라 해상도·프레임레이트·비트레이트를 동적으로 조절한다. WebRTC 혼잡 제어를 그대로 활용한다.
  • 변경 영역 최적화 — 정적인 화면에서는 dirty rect만 인코딩해 대역폭을 아낀다. 트러블슈팅 화면은 대부분 정적이라 효과가 크다.
  • 다중 모니터 — 모니터 선택 UI를 두고, 선택된 모니터만 캡처해 불필요한 전송을 막는다.
UAC 보안 데스크톱

UAC 승격 창(어둡게 변하는 화면)은 별도의 보안 데스크톱에서 뜨며, 일반 캡처로는 검은 화면이 된다. 이를 다루려면 Host를 Windows 서비스(Session 0)로 설치하고 데스크톱 전환 로직을 넣어야 한다. 06장에서 함께 다룬다.

06

관리자 권한 운용

지원자는 트러블슈팅을 위해 대상 PC를 관리자 권한으로 다룰 수 있어야 한다. 승격된 창(작업 관리자, 서비스 관리, 레지스트리 편집기), UAC 프롬프트, 잠금화면·로그인 화면까지 보고 조작해야 하기 때문이다. 이 요구사항이 Host의 아키텍처를 결정한다. Host는 프로토타입 단계부터 Windows 서비스(SYSTEM 권한) 기반으로 설계한다.

왜 서비스(SYSTEM)여야 하는가

일반 사용자 권한 프로세스로는 세 가지 벽에 막힌다. 첫째, UIPI(User Interface Privilege Isolation) — 낮은 권한 프로세스는 관리자 권한으로 뜬 창에 마우스·키보드 입력을 넣을 수 없다. 둘째, 보안 데스크톱 — UAC 승격 창과 Ctrl+Alt+Del(SAS), 잠금화면은 별도의 보안 데스크톱(Winlogon)에서 뜨며 일반 캡처·입력이 닿지 않는다. 셋째, Session 0 격리 — 서비스는 사용자 화면과 분리된 Session 0에 있어, 사용자 세션의 입력 데스크톱으로 명시적으로 전환해야 한다.

따라서 Host를 두 프로세스로 나눈다. 항상 SYSTEM으로 도는 서비스가 캡처·입력·데스크톱 전환 등 특권 작업을 전담하고, 로그인한 사용자 세션의 트레이 UI 프로세스가 동의 대화상자·세션 코드·상태 표시를 맡아 두 프로세스가 로컬 IPC(Named Pipe 등)로 통신한다.

관리자 모드(권한 상승) 흐름

세션은 기본적으로 로그인한 사용자 권한으로 조작한다. 지원자가 승격 창까지 다뤄야 할 때 "관리자 모드"를 요청하고, 이는 동의 게이트를 한 번 더 거친다. 대상 PC 환경에 따라 두 경로를 제공한다.

권한과 동의의 분리

관리자 권한 부여는 화면 보기·원격 제어와 별개의 승인 항목으로 다룬다. 동의 대화상자에서 "관리자 권한 허용"을 독립 토글로 두어, 대상자가 화면 공유는 허용하되 승격은 거부하는 선택이 가능하게 한다. 관리자 모드 진입·해제는 모두 감사 로그에 남긴다.

데스크톱 전환 구현

서비스는 WTSGetActiveConsoleSessionId로 현재 대화형 세션을 찾고, 캡처·입력 스레드를 사용자 데스크톱(Default)과 보안 데스크톱(Winlogon) 사이에서 OpenInputDesktop/SetThreadDesktop으로 전환한다. 이 전환 로직이 UAC 화면과 잠금화면 대응의 핵심이다. 기존 상용 도구(ConnectWise, Zoho Assist 등)의 "관리자 모드/UAC 제어"도 같은 원리를 쓴다.

07

입력 주입

지원자의 마우스·키보드 이벤트는 input 데이터 채널로 전달되어 Host 서비스에서 Win32 SendInput으로 주입된다. 좌표는 대상 화면 해상도 기준 정규화(0~1)해 보내고, Host가 실제 픽셀로 환산한다. 이렇게 하면 뷰어 창 크기·DPI 차이에 영향받지 않는다. 승격 창까지의 주입은 06장의 SYSTEM 서비스 구조가 전제된다.

주입 이벤트 종류

  • 마우스 — 이동, 좌·우·중클릭, 더블클릭, 드래그, 휠 스크롤. 절대좌표(정규화) 방식으로 전송한다.
  • 키보드 — 키 다운/업, 조합키(Ctrl·Alt·Shift·Win), 유니코드 문자 입력.
  • 특수키 시퀀스 — Ctrl+Alt+Del(SAS)은 일반 주입이 막히므로, 서비스가 SendSAS API로 별도 처리한다.
  • 클립보드 동기화 — 양방향 텍스트 클립보드 공유로 명령·경로 붙여넣기를 돕는다.
08

데이터 채널 프로토콜

화면은 미디어 트랙으로, 나머지 상호작용은 WebRTC 데이터 채널로 흐른다. 성격이 다른 트래픽을 여러 채널로 분리하면 신뢰성·순서 보장 정책을 각각 최적화할 수 있다.

채널신뢰성/순서페이로드용도

{
  "t": "mouse",
  "a": "move",

파일 전송 흐름

파일은 file-offer(메타데이터) → 수신 측 file-accept → 순번이 붙은 청크 스트림 → file-complete(체크섬 검증) 순으로 처리한다. 청크 크기는 16KB 안팎으로 잡고, 채널 버퍼가 임계치를 넘으면 송신을 잠시 멈추는 백프레셔를 적용한다.

09

보안·동의 모델

이 도구는 본질적으로 타인의 화면과 입력에 접근하므로, 보안과 동의는 부가 기능이 아니라 제품의 정체성이다.

Consent

명시적 동의 게이트

조작 시작 직전 Host가 대화상자를 띄우고, 대상자가 허용해야만 세션이 열린다. 화면 공유와 원격 입력을 각각 별도 토글로 승인하게 한다.

Visibility

상시 접속 표시

세션 중에는 화면 테두리·트레이 배지·상태 창으로 "지원자 접속 중"을 항상 표시한다. 대상자는 언제든 한 번의 클릭으로 즉시 종료할 수 있다.

Crypto

전 구간 암호화

시그널링은 TLS(WSS), 미디어·데이터는 WebRTC의 DTLS-SRTP로 종단 암호화한다. TURN 릴레이 경유 시에도 페이로드는 릴레이 서버가 복호화할 수 없다.

AuthZ

일회성 세션 인증

세션 코드는 일회성·단기 만료. 대역 외 전달된 PIN을 함께 요구해 코드 추측·재사용을 차단한다. 실패 횟수 제한과 룸 만료를 둔다.

Least Privilege

최소 권한

세션에서 허용된 동작만 수행한다. 초기에는 무인 접속을 배제하고, 필요 시 서비스 권한은 특권 작업에 한정한다.

Audit

감사 로그

세션 시작·종료, 접속 주체, 파일 전송 내역을 양측과 서버에 기록한다. 사후 추적과 오남용 방지에 쓴다.

종료 통제권

대상자는 세션 중 항상 우선한다. 종료 버튼, 단축키, 마우스를 일정 시간 강하게 움직이는 등의 "강제 회수" 제스처를 두어, 지원자가 조작 중이라도 즉시 통제권을 되찾을 수 있게 한다.

무인 접속을 도입한다면

상시 접속을 후속으로 넣는다면, 대상 기기별 사전 등록·기기 바인딩, 관리자 인증(가능하면 2FA), 접속 시 통지·사후 리포트, 접속 가능 시간대 제한을 반드시 함께 설계한다. 편의보다 통제가 우선이다.

11

동작 시나리오

가장 전형적인 유인 트러블슈팅 세션을 처음부터 끝까지 따라간다.

대상자
시스템
지원자
1

설치 및 실행

대상자가 배포된 Host 설치파일을 내려받아 설치하고 실행한다. 트레이에 앱이 올라온다. (최초 1회, 이후 재사용)

2

세션 시작

대상자가 "세션 시작"을 눌러 세션 코드와 PIN을 발급받는다. 이 순간 서버에 대기 룸이 생긴다.

3

코드 전달

대상자가 전화·메신저로 지원자에게 코드와 PIN을 불러준다. 대역 외 전달로 무작위 접속을 막는다.

4

접속 시도

지원자가 웹 뷰어를 열고 코드·PIN을 입력한다. 서버가 검증하고 시그널링을 시작한다.

5

동의

대상 PC에 동의 대화상자가 뜬다. 대상자가 "허용"을 누르면 화면 트랙과 입력 채널이 열린다.

6

진단·조작

지원자가 화면을 보며 마우스·키보드로 조작해 문제를 진단한다. 필요하면 채팅으로 안내하고, 로그 파일을 전송받는다.

7

패치 적용

지원자가 설정을 바로잡거나 패치 파일을 대상 PC로 보내 적용한다. 승격이 필요하면 Host의 관리자 권한으로 UAC 창까지 조작한다.

8

종료·기록

작업이 끝나면 어느 쪽이든 세션을 종료한다. 연결이 끊기고, 양측과 서버에 세션 요약·감사 로그가 남는다.

대체 흐름

  • P2P 실패 — 방화벽으로 직접 연결이 막히면 자동으로 TURN 릴레이 경로로 폴백해 세션을 유지한다(지연은 다소 증가).
  • 동의 거부 — 대상자가 거부하면 세션은 열리지 않고 지원자에게 "거부됨"이 표시된다.
  • 네트워크 단절 — 일시 단절 시 ICE 재협상으로 자동 재연결을 시도하고, 실패하면 세션을 안전하게 종료한다.
12

차별화 기능

TeamViewer·AnyDesk·RustDesk·Windows 원격 지원(Quick Assist)은 화면 공유와 원격 제어라는 기본기는 이미 성숙하다. 이들과 경쟁하려면 같은 기능을 더 잘 만드는 것으로는 부족하고, 트러블슈팅이라는 목적에 특화된 축에서 앞서야 한다. 방향은 세 가지다. 화면 조작에만 의존하지 않는 진단 도구, 반복 작업을 없애는 자동화·AI 보조, 그리고 사내 배포에 맞는 보안·거버넌스이다.

시스템 상태 대시보드

접속 즉시 CPU·메모리·디스크·네트워크·이벤트로그·시작프로그램·서비스 상태를 한 화면에. 화면 스트림 없이도 문제를 좁힌다.

원격 탐색기

파일시스템·레지스트리·서비스·프로세스를 화면 조작 없이 직접 탐색·편집. 느린 화면 조작을 건너뛴다.

자동화

Runbook 스크립트

자주 쓰는 진단·수정 스크립트(PowerShell 등)를 라이브러리로 두고 원클릭 실행. 결과를 세션 기록에 자동 첨부.

AI

AI 진단 어시스턴트

로그·이벤트를 요약하고 원인 후보와 조치를 제안. 승인 기반 실행으로 안전하게 자동화.

협업

세션 큐 · 이관

다수 대상자 대기열 관리, 다른 지원자로 세션 이관, 상급자 관전(read-only)으로 팀 지원.

기록

녹화 + 타임라인 주석

세션 전체를 녹화하고 주요 시점에 주석. 감사·재현·교육·인수인계에 활용.

보안

Self-hosted / On-prem

릴레이·시그널링을 내부망에 직접 운영. 트래픽이 외부 벤더를 거치지 않아 데이터 주권을 지킨다.

거버넌스

RBAC · 승인 워크플로

역할별 권한(보기/제어/관리자모드/파일전송), 관리자 모드·무인 접속에 대한 사전 승인 절차.

접근성

저대역 폴백

대역폭이 부족하면 화면 없이 진단·터미널·파일 채널만으로 작동하는 경량 모드로 자동 전환.

현실적 우선순위

모든 기능을 한 번에 넣을 필요는 없다. 초기 차별화는 시스템 상태 대시보드 + Runbook 스크립트로 시작하는 것이 비용 대비 효과가 크다. AI 어시스턴트와 협업 기능은 기본 세션이 안정화된 뒤 얹는다. 각 기능이 06~09장의 권한·보안 모델을 위반하지 않는지 항상 함께 검토한다.

Phase 12~3주

PoC — 시그널링 + 화면 보기

Go/ASP.NET 시그널링 서버와 SIPSorcery Host로 화면을 웹 뷰어에 스트리밍한다. WebRTC 연결·인코딩의 실현 가능성을 먼저 확인한다.

Phase 23~4주

원격 입력 + 서비스(SYSTEM) 골격

Host를 Windows 서비스(SYSTEM)와 트레이 UI 두 프로세스로 세우고, input 채널·SendInput 주입을 붙인다. 관리자 권한이 핵심 요구사항이므로 데스크톱 전환·UIPI 대응 골격을 이 단계에서 확보한다.

Phase 32주

동의·보안 모델

세션 코드·PIN, 동의 대화상자, 상시 표시, 즉시 종료, TLS/DTLS 확인, 감사 로그를 넣어 제품의 안전 골격을 세운다.

Phase 42~3주

NAT 통과·릴레이

coturn을 세우고 STUN/TURN을 통합한다. 방화벽 환경에서 P2P↔릴레이 폴백을 테스트한다.

Phase 53~4주

관리자 모드 · 보조 기능 · 차별화 1차

UAC·SAS·잠금화면 대응(관리자 모드)을 완성하고, 파일 전송·채팅·다중 모니터를 넣는다. 차별화 기능 중 시스템 상태 대시보드와 Runbook을 1차로 얹는다.

Phase 62주

배포·안정화

설치 패키지(서명 포함), 자동 업데이트, 적응형 품질 튜닝, 부하·장애 테스트로 마무리한다.
