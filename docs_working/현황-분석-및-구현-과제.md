# 현황 분석 및 구현 과제 (2026-10-23)

Codex 작업을 이어받아 코드 상태를 읽고 정리한 문서다. 임시 작업 문서이며 확정되면 `docs/`의 기준 문서(product-contract, architecture, protocol)를 먼저 갱신한 뒤 구현한다(AGENTS.md 규칙).

## 0. 목표 (사용자 확정 지시)

1. **NAT 통신은 무조건 된다.** 연결 가능 여부를 따지거나 시험·분기할 대상이 아니다. 코드는 "항상 연결되는" 것으로 단순하게 작성한다.
2. **대상 PC는 시작할 때 관리자 권한으로 한 번 실행하면 끝이다.** 그 뒤 대상자가 할 일은 없고, 조작하는 쪽이 마음대로 조작할 수 있어야 한다. 화면·입력·관리자/UAC·파일·클립보드·Runbook·모니터 전환 모두 해당한다.
3. **두 PC는 서로 신뢰 관계다.** 신뢰 검증·본인 확인·승인 절차·방어적 제한을 위한 코드는 필요 없다.

이 세 줄이 아래 모든 판단의 기준이다. 기존 AGENTS.md의 "대상자 통제권 우선/건별 승인/최소 권한" 원칙과 충돌하는 부분은 사용자의 최신 지시가 우선하므로 AGENTS.md와 `docs/`도 함께 고쳐야 한다(§5).

## 3. 잘못된 것 (목표와 어긋나거나 결함인 것)

### 3-A. NAT/P2P — 현재 구성으로는 NAT 넘어 연결되지 않는다 (치명)

"NAT은 무조건 된다"를 코드가 뒷받침하지 않는다. 이 부분이 가장 먼저 고쳐야 한다.

1. **STUN 서버가 어디에도 설정되지 않는다.**
   - Host 기본값 `StunServers = []` (`ScreenShareOptions.cs:15`), 배포 설정에서도 채우는 곳이 없다.
   - 시그널링이 Host/Viewer에 내려주는 ICE 서버는 TURN 전용이다(`server.go`의 `iceServers`, `turn.go`). TURN URL이 없으면 빈 목록이다.
   - 결과: srflx 후보가 만들어지지 않아 같은 LAN이 아니면 직접 연결 후보가 없다. 브라우저도 같은 상태다.
2. **coturn 배포 설정이 UDP를 끈다.** `deploy/coturn/docker-compose.yml` 주석: "TCP 25002/25003만 listen, UDP listening은 끈다". STUN은 UDP가 기본이고 SIPSorcery·브라우저 모두 TCP STUN을 기대하기 어렵다. 즉 STUN 용도로 쓸 수 없다.
3. **Host WebRTC 포트 범위가 27002~27099로 고정**되어 있고(`ScreenShareSession.cs:270`) 방화벽 규칙도 이 범위에 묶인다. 포트가 점유되면 실패한다. 범위 자체는 개발 포트 대역 규칙 준수라 문제없으나, 폴백 처리가 없다.
4. **TURN/릴레이 잔재가 남아 있다** — 현재 규격(P2P only)과 불일치:
   - `ScreenShareOptions.ForceRelay`, Host/Viewer의 relay 정책, Viewer `?relay=1`.
   - 운영 모드(`RA_MODE=production`)는 TURN URL·secret이 없으면 서버가 **시작을 거부**한다(`main.go:165`).
   - `turn-refresh` / `turn-credentials` 메시지와 8분 주기 갱신 루프(`RefreshLoop`), 연결 끊김 시 복구가 이 경로를 재사용한다(`ScreenShareSession.cs:372-402`). 이름과 달리 지금은 "전송 재구성" 기능인데, TURN 구성이 있다는 가정이 서버 쪽 검사(`server.go:373`)에 섞여 있다.
   - `docs/`·`deploy/coturn/` 문서와 compose가 TURN 운영을 전제로 쓰여 있다.
5. 하지만 STUN만으로는 대칭형 NAT(일부 통신사/기업망)을 통과할 수 없다. "무조건 된다"가 사실이려면 다음 중 하나가 환경 가정으로 보장돼야 한다: (a) 양쪽이 같은 사설망/VPN, (b) 한쪽이 공인 IP 또는 포트 포워딩, (c) 대칭형 NAT가 아님. 사용자가 이 보장을 선언했으므로 코드는 STUN + host 후보만으로 단순하게 만들고, 가정을 문서에 한 줄로 명시한다.

### 3-B. "한 번 관리자 실행하면 끝"이 지켜지지 않는 지점

1. **코드/PIN 전달이 아직 필요하다.** 대상자가 9자리 코드와 4자리 PIN을 지원자에게 알려줘야 한다(Tray가 표시, Viewer 폼에 입력). "아무것도 안 해도 된다"와 정면 충돌한다. 서로 신뢰한다면 고정 식별자(예: 대상 PC가 시그널링에 등록한 고정 ID/이름)로 지원자가 목록에서 선택해 접속하는 방식이 맞다.
2. **허가에 시간 제한이 있다.** 실행 후 10분 안에 지원자가 붙지 않으면(`ClaimDeadline`) 허가 소멸, 붙어도 2시간이면 세션 종료(`InitialSupportGrant.Validate`, 감독 루프 `HostSessionSupervisor.cs:90`). 원하는 동작은 "프로그램을 종료할 때까지 유지"다.
3. **지원자가 끊으면 허가가 사라진다.** `peer-left` → `EndSession`(`ScreenShareSession.cs:199`) → `StopHelper`가 `initialLaunch=null`로 지운다(`HostSessionSupervisor.cs:430`). 이후에는 Tray에 "지원 코드를 만들면 대상자의 승인 후 연결한다"가 뜨고 수동 경로가 된다. 브라우저 새로고침·네트워크 순단 한 번이면 대상자가 다시 관리자 실행해야 한다.
4. **세션 코드가 일회용(`consumed`)이고 슬롯이 하나**(`slot-taken`)라 재접속·다른 브라우저로의 접속이 막힌다.
5. **허가가 런처 프로세스에 묶여 있다.** 소비 시 런처 PID·시작 시각이 그대로여야 한다(`InitialSupportLaunch.Consume`). 런처를 닫거나 재부팅하면 무효다. 재부팅 후 자동 복구가 없다는 점은 의도된 보안 설계이지만 새 요구와는 맞지 않는다(재부팅 후 재실행은 허용하더라도, 런처가 살아 있는 동안은 계속 유지돼야 한다).
6. **수동 경로 전체가 그대로 남아 있다.** 허가가 없으면 `ConsentWindow`(권한 체크박스), `AdminConsentWindow`, `ActionConsentWindow`, 파일·클립보드·모니터·Runbook 건별 승인, 120초 승인 타임아웃이 동작한다. 새 요구에서는 모두 불필요한 코드이며, 한 번 어떤 이유로 허가가 풀리면 대상자가 조작해야 하는 상태로 떨어지는 원인이 된다.

### 3-C. "마음대로 조작"을 막는 제한

1. **관리자 모드가 별도 단계다.** Viewer에서 관리자 진입을 요청해야 하고, 진입 중에는 일반 화면 캡처가 정지·교체된다. 관리자 모드에서는 **모니터 전환 불가**(`ScreenShareSession.cs:424`, `startup-preparation.md:24`). 일반 데스크톱과 관리자(UAC) 데스크톱을 오가는 작업 중에 화면이 끊기거나, 승인 없이 데스크톱이 바뀌면 세션이 종료된다(`ScreenShareSession.cs:485`).
2. **일반 Helper가 일반 권한이라 관리자 창에 입력이 안 들어간다**(UIPI). 그래서 관리자 모드·AdminHelper 이중 구조가 필요해졌다. 대상자가 이미 관리자로 실행했으므로 Helper를 처음부터 상승 권한(또는 SYSTEM)으로 사용자 세션에 띄우면 이 이중 구조 상당 부분이 불필요해질 수 있다. 설계 변경이 크므로 검증 후 결정한다(§4-3 P1).
3. **보안 데스크톱(UAC 화면) 캡처는 DXGI 경로만 쓰며 GPU별 동작이 미확인이다**(`startup-preparation.md:28`). 하이브리드 GPU에서 DXGI 복제가 실패한 전례가 AGENTS.md에 있다. UAC 조작이 핵심 요구인데 실측이 없다.
4. **입력 제한**: 텍스트 4096자, 채팅 빈도, 파일 청크·한도, 클립보드 2초 대기·16건 상한, Runbook은 등록된 카탈로그만 실행 가능(`RunbookCatalog`). "마음대로"라면 임의 명령 실행이 막혀 있다는 점이 가장 큰 제약이다. 요구 범위(원격 셸이 필요한지)를 정해야 한다. 현재는 AGENTS.md가 임의 원격 셸을 1차 범위 밖으로 둔다.

### 3-D. 불필요한 신뢰 검증·방어 코드 (제거 대상)

신뢰 관계가 전제이므로 아래는 기능이 아니라 부담이다. 연결 실패의 원인이 되기도 한다.

- 코드+PIN 인증, 시도 횟수 제한, 10분 TTL, 발급 속도 제한(`handleCreateSession`).
- 접속자 이름 검증과 "별도 연락으로 확인" 안내, 지원자 신원 바인딩(`consent-request` 바인딩).
- 승인 세대(`permissionGeneration`) 검사, 권한 스냅샷, 감사 실패 시 중단 정책 등 기능 단위 권한 게이트(`PermissionGate`, `FeatureContract`, `AdminAuthorization`). 전 권한을 항상 주면 필요 없다.
- 감사 로그 저장소가 시그널링 시작 조건(`OPERATOR_SECRET`, `AUDIT_DIR`, 운영 node credential). 서버 시작을 막는 요소다.
- 서명 설치·릴리스 매니페스트·업데이트 서명 검증, 보호 경로 ACL 검사, 개발/운영 분리 마커(`dev-owner.json`)가 시작 경로에 강제된다. 개발 중에는 가장 큰 마찰이다.
- 입력 복원 감독 프로세스(Recovery), 종료 관측 probe(`local-stop-observation`), 서비스 상태 ndjson, E2E 전용 `CaseTrace`.

단, 대상자의 즉시 종료 수단과 접속 중 표시는 사용자가 유지하라고 한 적이 없으므로 제거 여부를 정하되, 대상자가 직접 끌 수 있는 Tray 종료 버튼 하나는 남기는 편이 안전하다(프로그램 종료 = 권한 폐기).

1. **작업 중 파일 31개가 커밋되지 않은 채 남아 있다**(`git status`): 시작 준비(`StartupPreparation.cs`, `InitialSupportLaunch.cs`, `DevSupportLauncher.cs`, `app.manifest`), 준비 스크립트 2개, 회귀 테스트, 수동 E2E 스크립트 17개(`scripts/manual-e2e-*`, `manual_e2e_*.py`). 최신 커밋 메시지는 "멍청이가 한것"이라 이력으로 의미가 없다. 핵심 신규 기능이 전부 미커밋이다.
2. **`docs_working/`이 비어 있다**(커밋 `44b956b`에서 전부 삭제). 구현계획(`원격제어-구현계획.md`)이 AGENTS.md 여러 곳에서 기준 문서로 지정돼 있으나 존재하지 않는다. 진행 상태를 볼 기준 문서가 없다.
3. **문서가 새 요구와 모순**된다: `docs/product-contract.md`, `architecture.md`, `workflows.md`는 건별 승인·TURN 경유·코드/PIN·동의 모델을 전제로 한다. AGENTS.md "동의 모델 — 구현 시 반드시 지킬 것"과 설계 원칙 1·2도 마찬가지다.

6. 전용 시험 도구(`F:/github/DesktopTestDriver`)와 `.artifacts/` 아래 후보 빌드가 저장소 작업 디렉터리에 섞여 있다(`.artifacts/c01-candidate-*`, `browser/node_modules`). `.gitignore` 여부를 확인해야 한다.

## 4. 더 구현해야 할 것 (우선순위)

### P0 — 이것이 없으면 요구 자체가 성립하지 않는다

1. **NAT 연결 구성 마무리**
   - Host 기본 설정에 STUN 서버를 채운다(공인 STUN 또는 자체 UDP STUN). 시그널링이 STUN 목록을 Host/Viewer 양쪽에 내려주도록 한다. coturn을 STUN 용도로 쓸 거면 UDP 27001로 listen하도록 compose를 고친다(AGENTS.md의 UDP 대역 규칙 사용).
   - TURN/ForceRelay/`turn-refresh` 경로 제거, `production` 모드의 TURN 필수 검사 제거. "전송 재구성"은 이름을 바꿔 ICE 재시작으로 정리.
   - 연결 가정(§3-A-5)을 문서에 명시.
2. **상시 접속 모델 도입 (코드/PIN 제거)**
   - 대상 PC가 관리자 실행 시 시그널링에 고정 ID로 등록. 지원자는 목록 또는 ID로 접속하며 PIN 없음.
   - 허가를 런처 프로세스 수명에 묶고(시간 제한 없음), 지원자 연결이 끊어져도 세션을 종료하지 않고 재접속을 기다린다.
   - 재접속·다중 Viewer(교체 접속)를 허용한다.
3. **전 권한 상시 부여**: 연결되면 무조건 capability 255를 부여하고 승인 창·승인 타임아웃·건별 승인 코드를 삭제한다.

### P1 — 조작 품질

1. **관리자/UAC 조작을 끊김 없이**: Helper를 상승 권한으로 띄워 일반·관리자 창 입력을 한 경로로 처리할 수 있는지 먼저 실험으로 확인(이중 구조 단순화 여부 결정). 보안 데스크톱 전환 시 화면 자동 전환, 모니터 전환 제한 해제(관리자 헬퍼 모니터 재바인딩).
2. **보안 데스크톱 캡처 실측**: 두 PC(GPU 구성 상이)에서 UAC 화면이 실제로 보이고 조작되는지 확인. 실패 시 폴백 설계.
3. **조작 범위 확정**: 임의 명령 실행(원격 셸)이 필요한지 결정. 필요하면 Runbook 카탈로그 외에 직접 실행 채널 추가. 필요 없다면 현 상태 유지.
4. **Viewer 새로고침/재접속 복원**, 모니터 선택·품질 UI 정리.

### P2 — 정리

1. 불필요한 신뢰/감사/서명 검증 코드 제거 또는 비활성(§3-D). 한 번에 지우지 말고 기능 게이트부터 단계적으로 걷어내며 빌드·테스트를 통과시킨다.
2. 시그널링 단순 모드 추가: 인증서·operator secret·감사 디렉터리 없이 시작 가능, 허용 대역 사설망.
3. 대형 한 줄 코드 정리, 중복 try/catch 제거.

### P3 — 이후

설치/업데이트 서명 경로, 자동 업데이트, 인코더 장치별 검증(HW/SW), 성능 실측(지연·FPS·비트레이트는 추정하지 않고 측정값만 기록).

## 5. 먼저 고칠 문서 (코드 변경 전)

1. `AGENTS.md`: 설계 원칙·동의 모델·"최초 관리자 실행 UX" 항을 새 요구(상시 신뢰, 전 권한 자동, 코드/PIN 제거)로 교체. E2E 준비 지침은 그대로 둔다(화면 점유 시험은 여전히 사용자 허락 후).
2. `docs/product-contract.md`, `architecture.md`, `workflows.md`, `protocol.md`: 동의 메시지·승인 필드·TURN 필드 삭제, 상시 접속/등록 메시지 추가.
3. `docs/startup-preparation.md`: 허가 만료·소비 규칙을 "런처 수명 동안 유지"로 변경.
4. 구현계획 문서를 `docs_working/`에 새로 만들어 위 P0~P2를 E 단위로 쪼개 추적(삭제된 `원격제어-구현계획.md`를 대체).

## 6. 제안하는 진행 순서

1. 사용자 확인: §7의 결정 사항.
2. 현재 미커밋 31개 파일을 의미 있는 메시지로 한 번 커밋해 기준선을 만든다(요청하면 진행).
3. 문서 갱신(§5) → P0-1(NAT/STUN) → P0-2/3(상시 접속·전 권한) → 빌드·단위 테스트.
4. P1 실험(상승 권한 Helper, UAC 캡처)은 사용자가 시험 재개를 허락한 뒤 두 PC에서 짧게 실행한다. 화면 점유 시험은 AGENTS.md의 E2E 준비 지침(사전 계획·상한 시간·정리 절차)을 따른다.

## 7. 사용자 결정이 필요한 항목

| 질문 | 권장 |
|---|---|
| 접속 식별을 코드/PIN 대신 고정 ID로 바꿔도 되는가 | 예. 신뢰 관계 전제와 "아무것도 안 해도 됨"에 맞다 |
| 허가 유지 기간 | 런처 프로세스(프로그램)가 살아 있는 동안 |
| 지원자가 끊긴 뒤 | 세션 유지하고 재접속 대기 |
| 임의 원격 셸 필요 여부 | 필요하면 P1-3에서 추가. 현재는 없음 |
| 서명·감사·ACL 검증 | 개발 단계에서는 비활성, 배포 단계(P3)에서 재검토 |
| 대상자가 끌 수 있는 종료 버튼/접속 표시 | 종료 버튼 하나는 유지 권장 |

## 8. 한계와 미검증 사항

- 이 문서는 정적 코드 읽기와 빌드·단위 테스트 실행만 근거로 한다. 실제 연결, 캡처 품질, UAC 조작, 방화벽 동작은 실행해 보지 않았다.
- 입력 주입(`InputSession`, `SendInput`), 캡처 구현 상세, AdminHelper IPC, Runbook 워커는 구조 확인에 그치고 결함 여부를 코드 리뷰하지 않았다. P1 착수 전에 해당 영역을 별도로 리뷰한다.
- `STUN 미설정` 판단은 저장소 안의 설정과 코드 기준이다. 대상 PC에 이미 배포된 `host.settings.json`에 값이 들어 있을 수 있으므로 B 머신 설정을 읽기 전용으로 확인하면 확정된다.
