# 두 PC E2E 테스트 사전 준비

2026-10-08 사용자 지시로 추가 대화형 검증은 구현과 코드 리뷰 뒤로 미룬다. 최종 두 PC F01~F12는 별도 수행한다. 아래 기존 PoC 예시는 과거 준비 기록이며 현행 제품 시험의 실행 지시로 사용하지 않는다.

<a id="required-execution-plan"></a>

## 실행 전 필수 계획·준비표

**계획·준비·명령/판정/수집/정리의 사전 리뷰가 끝나지 않으면 시험을 시작하지 않는다.** 제품 화면·입력·서비스·UAC·잠금의 단일 PC 실증에도 적용한다. E 단계에서 준비 절차를 작성·리뷰하고 E 전체 완료 후 V/F 단계에서 사전 점검·검증을 실행한다. 이 표는 실행 준비 양식이며 별도 구현 진행표가 아니다. E/V/F 상태는 통합 구현계획에서만 관리한다.

| 실행 전 확정할 항목 | 작성할 내용 |
|---|---|
| 목적·범위 | 대응 V/F, 이번 묶음에서 확인할 기능/결함, 재사용/생략할 기존 검사, 실행 중 추가하지 않을 경계 |
| 고정 후보 | commit, 바이너리 hash/버전, 설정, 변경 파일 포함 여부, 시험 중 후보를 바꾸지 않는 방법 |
| 전제 조건 | 도구/모듈/FFmpeg, 인증서/포트/계정·Session·desktop, 사람이 개입할 단계와 복귀 수단 |
| 대상과 입력 | 정확한 창/모니터/실제 물리 좌표·DPI, foreground/snapshot 최신성, 같은 머신의 포커스/reset 간섭 대책 |
| 소유 자원 | 미리 확인한 PID/이미지 경로, 시험 창·브라우저·서비스·배치·임시 파일의 식별자와 소유 범위 |
| 단계별 실행 | 순서, 정확한 명령/동작, 준비 완료 신호, 관찰할 기대 상태, 실패 분기 |
| 판정과 증거 | 기능별 PASS/FAIL, 실행 ID/시간선, 영상 변화/채널/입력 상태·로그, 실패 직전 상태 수집 |
| 시간과 중단 | 각 시나리오와 전체 숫자 상한, 사용자 화면 점유 예상 시간, 첫 실패/신호 누락/초과 시 중단 조건 |
| 정리와 복구 | 입력 해제·세션/소유 프로세스/시험 창 종료·임시 서비스/배치 정리, 사용자 일반 작업 복귀 확인 |
| 사전 리뷰/점검 | 명령·경로·좌표·판정·수집·정리의 리뷰 결과, 입력을 주입하지 않는 준비 점검 결과, 미확정/실패 항목 없음 |

화면 점유 묶음은 기본 5분 이내로 설계하고 준비·빌드·게시·설치 준비·원인 분석은 점유 구간에 넣지 않는다. 긴 성능/부하 검사는 화면 점유 없는 별도 묶음으로 계획한다. 실행 직전 목적·점유 예상 시간·중단 조건을 사용자에게 짧게 알린다. 예상 시간을 성공 보장으로 표현하지 않는다.

첫 실패·준비 신호 누락·시간 초과 시 중단·수집·정리부터 수행한다. 화면을 점유한 채 코드 수정·환경 탐색·다음 시나리오를 진행하지 않는다. 정리 실패 시 일반 작업 복구를 최우선으로 수행한다. 원인과 준비가 바뀌지 않은 동일 시험은 반복하지 않는다. 재실행은 원인 분석·수정/준비 변경·예상 결과·판정/정리를 리뷰한 뒤 영향받은 시나리오로 한정한다. 공유 검사 결과를 여러 V/F에 연결해 중복 실행을 줄인다.

실행 후 실제 화면 점유 시간·확인한 결과/새 결함·정리/복귀 결과를 기록한다. 시간이 많이 들고 결과가 적었다면 다음 실행 전에 계획과 관측 수단을 개선한다. 준비 완료나 프로세스 기동은 기능 PASS가 아니다. 아래 PoC 예시의 경로·명령·좌표를 검토 없이 제품 시험에 복사하지 않는다.

후속 시험은 화면을 점유하기 전에 빌드·모듈 검사·FFmpeg hash/ABI 검사·후보 파일 목록과 해시·설정·포트·소유 프로세스·cleanup 경로를 비대화형으로 점검한다. 코드/PIN·화면 원본은 ignored artifact에만 저장한다. 설치/게시/브라우저 준비는 입력 시험 시간에 포함하지 않는다.

화면을 점유하는 구간에는 동일 머신의 포커스 간섭을 피하도록 headless Viewer와 .NET `RemoteAssist.InputTarget`을 사용한다. 창 위치를 고정 추측하지 않고 snapshot의 실제 물리 좌표와 승인한 모니터 geometry로 환산한다. snapshot 최신성·foreground·채널 준비·영상 디코딩·키 down 확인 뒤에만 fault를 요청한다. 서비스 PID/이미지 경로는 미리 확인한다. 각 시나리오에 시간 상한을 두고 실패하면 즉시 입력 해제·세션 종료·시험 창/브라우저 종료·임시 서비스와 배치 정리를 수행한다. UAC/잠금 시나리오는 별도 짧은 구간으로 묶고 사용자 조작 대기를 전체 시험에서 분리한다. 준비가 실패하면 대화형 구간을 시작하지 않는다.

작성일: 2026-10-08. 기준 커밋: `a2c22a3`. 이 문서는 **향후 테스트를 위한 준비 절차**이며, E2E 통과 기록이 아니다. 실제 테스트 때는 해당 커밋의 구현 상태와 명령을 다시 확인한다.

## 1. 먼저 알아둘 것

PC 두 대면 같은 LAN에서 화면 공유 E2E를 시작할 수 있다. 다만 Codex가 반복 실행하려면 **대상 PC의 명령 실행·파일 전달·로그 회수 경로**, **로그인된 사용자 화면에서 Host를 실행하는 방법**, **Viewer 브라우저 관찰·자동화 수단**까지 필요하다.

현재 저장소에는 두 PC를 자동으로 준비하고 테스트하는 완성된 E2E 하네스가 없다. 이 문서의 준비를 마쳐도 자동화 스크립트·브라우저 제어 연결은 테스트 작업에서 따로 마련해야 한다. SSH 설치만으로 Codex에 원격 PC 접근 권한이나 도구가 자동 부여되는 것도 아니다. 테스트를 진행하는 Codex 환경에서 네트워크·명령 실행 권한을 확인해야 한다.

| 구분 | 현재 가능한 범위 | 준비 시 주의점 |
|---|---|---|
| 화면 공유 PoC | HostRun → Go 시그널링 → 브라우저 영상 수신 | 실제 E2E 대상으로 삼는다 |
| 캡처·인코더 진단 | CaptureDump, HostRun `--encoder-check` | 도구 종료 코드만으로 정상 판정하지 않는다 |
| 마우스·키보드, 동의 UI, 서비스·트레이 연동 | 미구현 또는 골격 | 준비 완료와 기능 구현 완료를 구분한다 |
| UAC·SAS·잠금화면 제어, 파일·채팅 | 미구현 | 이후 기능별 승인·검증 환경이 필요하다 |
| TURN | 설정 초안만 있고 앱 통합 없음 | coturn을 켜는 것만으로 릴레이 E2E가 되지 않는다 |

**현재 PoC는 연결되면 화면을 보내며 대상자 동의 UI가 없다.** 본인 소유의 테스트 PC와 비민감 화면만 사용하고, 참여자가 화면 공유를 명시적으로 허용한 시간에 실행한다. 공용 인터넷에 현재 HTTP/WS 서버를 노출하지 않는다.

## 2. 권장 배치와 준비 순서

이 문서에서는 이 PC를 **A**, 다른 집 PC를 **B**로 부른다. 기존 실행 가이드의 A/B 표기는 다른 배치 예시이므로 혼동하지 않는다. 역할이 같으면 시그널링을 B나 별도 PC에 두어도 된다.

| 항목 | PC A — 이 PC | PC B — 다른 PC |
|---|---|---|
| 역할 | Codex 작업 환경, 시그널링 서버, Viewer | 화면을 공유하는 Host |
| 예시 LAN IPv4 | `192.168.10.10` | `192.168.10.20` |
| 예시 저장소 | `F:\github\KnockHB` | `C:\work\KnockHB` |
| 필수 프로그램 | Git, Go toolchain, Edge 또는 Chrome | Git, .NET 10 SDK, FFmpeg shared DLL |
| 원격 반복 작업 | OpenSSH Client | OpenSSH Server, 테스트 계정 |
| 로컬 상태 | Viewer 브라우저를 열 수 있는 사용자 세션 | 실제 모니터, 로그인·잠금 해제된 사용자 세션 |

위 주소와 B 경로는 **예시**다. 아래 명령을 실행하기 전에 실제 값으로 바꾼다. 첫 시험에는 기존 두 PC를 그대로 사용하면 된다. 추가 GPU·VM·TURN 서버 구매나 설치는 필수가 아니다.

준비 순서는 다음과 같다.

1. 두 PC를 같은 신뢰할 수 있는 LAN에 연결하고 실제 주소를 기록한다.
2. B에 테스트 계정과 화면을 준비하고 로컬 캡처·인코딩부터 확인한다.
3. A의 시그널링을 B에서 접근할 수 있게 한다.
4. B에서 Host를 직접 실행하고 A에서 영상 수신을 수동 확인한다.
5. 반복 검증이 필요하면 SSH·파일 회수·사용자 세션 실행·브라우저 자동화를 연결한다.
6. 기본 LAN 검증 이후 별도 네트워크, 장애, 다중 모니터 등으로 확장한다.

## 3. 두 PC 공통 준비

### 장비와 계정

- [ ] PC 이름, OS 버전·빌드, CPU, RAM, GPU, 드라이버 버전을 기록한다.
- [ ] Windows x64 환경인지 확인한다. 프로젝트의 Windows TFM 하한은 빌드 19041이지만, 실제 지원 판정은 실행 결과로 한다.
- [ ] B에는 테스트 전용 일반 사용자 계정을 준비한다. 관리자 계정은 설치·방화벽 설정 등 필요한 순간에만 사용한다.
- [ ] B의 실제 모니터를 연결하고 켠다. 처음에는 단일 모니터·고정 해상도/DPI로 시작한다.
- [ ] B에 로컬 로그인하고 잠금을 해제한다. RDP 화면을 기본 캡처 환경으로 사용하지 않는다.
- [ ] 전원을 연결하고 시험 중 절전·최대 절전·자동 재부팅이 발생하지 않도록 조정한다. 변경 전 설정을 기록한다.
- [ ] 무인 상태로 잠금 해제해 두지 않는다. 잠금·절전 동작은 기본 연결 성공 후 별도 시험한다.
- [ ] 양쪽 날짜·시간을 동기화하고 로그에 사용할 시간대와 테스트 시작 시각을 기록한다.
- [ ] 바탕화면·알림·브라우저·메신저에 개인정보, 업무 문서, 비밀번호가 노출되지 않게 정리한다.
- [ ] B의 키보드·마우스에 사람이 접근할 수 있게 한다. Host 중단·잠금 해제·네트워크 복구를 위한 마지막 수단이다.

읽기 전용 확인 명령이다. 일반 PowerShell에서 실행한다.

```powershell
hostname
whoami
Get-CimInstance Win32_OperatingSystem | Select-Object Caption, Version, BuildNumber, OSArchitecture
Get-CimInstance Win32_Processor | Select-Object Name
Get-CimInstance Win32_ComputerSystem | Select-Object TotalPhysicalMemory
Get-CimInstance Win32_VideoController | Select-Object Name, DriverVersion
Get-NetIPConfiguration
Get-NetConnectionProfile
Get-Date -Format o
quser
```

`quser`의 사용자·세션 ID와 실제 화면의 계정을 함께 확인한다. 원격 로그인 성공이나 프로세스 존재만으로 올바른 데스크톱을 캡처한다고 판단하지 않는다.

### 테스트 데이터

B의 화면에 PC 이름과 구분 가능한 문구를 띄우고, 창 이동·스크롤 등 지속적으로 변화하는 내용을 준비한다. 정지 화면 한 장만 보이면 영상이 멈춰도 알아차리기 어렵다. 전송 프레임 수 증가와 **Viewer에서 실제로 보이는 변화**를 함께 확인한다.

## 4. 소스·런타임·FFmpeg 준비

### 소스 버전 고정

A와 B 모두 같은 커밋을 사용한다. B에 Git 접근 권한을 줄 수 없다면 A에서 만든 테스트 패키지를 전달할 수 있지만, 첫 준비는 소스 checkout과 SDK 실행이 단순하다.

저장소 루트에서 확인한다.

```powershell
git rev-parse HEAD
git status --short
```

변경 파일이 있으면 테스트 기록에 포함한다. 테스트 도중 한쪽만 최신 main으로 갱신하지 않는다. 소스 대신 바이너리를 전달한다면 commit, 빌드 구성, x64 여부, .NET 런타임 포함 여부와 파일 해시를 기록한다.

### PC A — 시그널링·Viewer

- [ ] 저장소 `server/signaling/go.mod`의 요구 버전을 충족하는 Go toolchain을 준비한다. 작성 시점 선언은 `go 1.27`이다.
- [ ] Edge 또는 Chrome을 준비하고 실제 버전을 기록한다. 브라우저 확장이 없는 전용 테스트 프로필을 사용한다.
- [ ] Viewer는 정적 HTML/JS이므로 앱 실행 자체에 npm 빌드가 필요하지 않다.
- [ ] Node.js는 향후 브라우저 테스트 하네스나 JS 검사에 사용할 경우에만 추가 준비한다.

```powershell
go version
Push-Location server/signaling
go mod download
go build ./...
go test ./...
go vet ./...
Pop-Location
```

각 명령의 종료 코드와 출력 내용을 확인한다. 자동 toolchain 다운로드나 의존성 복원이 차단되면 테스트 당일 전에 네트워크·프록시·캐시를 해결한다. 버전 요구를 임의로 낮춰 통과시키지 않는다.

### PC B — Host

- [ ] .NET 10 SDK와 Windows 대상 프로젝트 빌드에 필요한 구성요소를 준비한다.
- [ ] NuGet 패키지를 복원할 수 있게 한다. Git·NuGet 인증 비밀을 문서나 로그에 넣지 않는다.
- [ ] GPU 드라이버 버전을 기록한다. 비교 시험 중에는 드라이버를 바꾸지 않는다.
- [ ] [FFmpeg 안내](../third_party/ffmpeg/README.md)에 맞는 x64 shared DLL 전체 세트를 `third_party/ffmpeg/bin/`에 배치한다.
- [ ] FFmpeg 8.1 ABI, 프로젝트의 LGPL 빌드 정책, `libx264` 제외 여부를 확인한다. 임의의 최신 FFmpeg로 대체하지 않는다.
- [ ] FFmpeg의 출처·정확한 버전·빌드 옵션·SHA-256을 기록한다. DLL은 Git에 포함되지 않으므로 별도 전달이 필요하다.

```powershell
dotnet --info
dotnet restore RemoteAssist.slnx
dotnet build RemoteAssist.slnx --no-restore
Get-ChildItem third_party/ffmpeg/bin -Filter '*.dll'
Get-ChildItem third_party/ffmpeg/bin -Filter '*.dll' | Get-FileHash -Algorithm SHA256
```

네이티브 DLL 존재와 C# 빌드 성공은 실제 인코딩 성공을 보장하지 않는다. 다음 진단은 **B의 로그인된 바탕화면에서 연 PowerShell**에서 실행한다.

```powershell
dotnet run --project tools/RemoteAssist.CaptureDump -- --list
dotnet run --project tools/RemoteAssist.CaptureDump -- --backend wgc --monitor 0 --frames 5 --out .artifacts/e2e/preflight-wgc
dotnet run --project tools/RemoteAssist.HostRun -- --encoder-check
```

PNG가 요청한 5장 생성됐는지, 의도한 모니터인지, 크기·방향·화면 내용이 맞는지 직접 본다. 인코더 검사에서는 실제 선택 인코더와 출력 프레임 수를 확인한다. 현재 검사 도구에는 거짓 성공 가능성이 있어 성공 표시나 종료 코드 0만으로 판정하면 안 된다(R01/R17). DXGI 별도 시험은 `--backend dxgi`와 다른 출력 디렉터리로 수행한다.

현재 앱에는 MySQL이 필요하지 않다. LAN 기본 테스트에는 Docker·coturn·Windows 서비스 등록도 필요하지 않다.

## 5. LAN·방화벽 준비

### 주소와 통신 범위

- [ ] 가능하면 첫 시험은 유선 LAN으로 한다. Wi-Fi라면 게스트 네트워크·AP client isolation으로 단말 간 통신이 막히지 않는지 확인한다.
- [ ] A와 B의 주소를 기록하고 필요하면 공유기 DHCP 예약을 사용한다.
- [ ] 불필요한 VPN·가상 어댑터의 존재를 기록한다. 제거하거나 보안 프로그램을 끄지 말고 실제 선택 경로를 확인한다.
- [ ] 사설 네트워크 프로필은 신뢰할 수 있는 집 LAN에만 적용한다.
- [ ] 방화벽 전체 해제, 백신 전체 해제, 공유기 DMZ·인터넷 포트포워딩은 하지 않는다.

| 용도 | 방향·포트 | 준비 기준 |
|---|---|---|
| 시그널링·Viewer | B → A TCP `25001`; A의 Viewer도 동일 서버 사용 | A의 실제 LAN IP에 바인딩하고 B 주소만 인바운드 허용 |
| SSH 관리 — 선택 | A → B TCP `25002` | 이 테스트 전용 새 listener의 예시. A 주소만 허용 |
| WebRTC 미디어 | A ↔ B, ICE가 선택한 경로 | TCP 25001과 별개다. 현재 로컬 UDP 포트 범위는 코드에서 고정하지 않는다 |
| 외부 STUN | 앱 기본값 `stun.l.google.com:19302` | 로컬 listener가 아닌 외부 목적지다. 인터넷 차단 여부를 기록 |
| 향후 TURN | 별도 설계·통합 후 확정 | 앱 통합, 인증, listening/relay 포트, TLS, 외부 도달성 검증이 선행 |

프로젝트의 개발용 할당 대역은 TCP `25001~25199`, UDP `27001~27199`다. **현재 WebRTC 포트 할당은 이 대역으로 강제되지 않는다.** UDP `27001~27199`만 열면 반드시 된다고 가정하지 않는다. 사용 중인 Host 실행 파일과 테스트 브라우저에 대해 상대 PC로 제한한 규칙이 필요한지 확인하고, 포트 정책과의 차이를 시험 기록에 남긴다. 엄격한 포트 제한이 필수인 환경에서는 미디어 포트 제어 구현을 먼저 해결해야 한다.

Windows Defender 방화벽에서 규칙을 만들 때는 이름, 프로그램 경로 또는 포트, 프로필, 상대 IP, 변경 전 상태를 기록한다. 첫 준비에는 보안 고급 설정 UI로 검토하며 만들면 된다. 기존 관리용 규칙을 일괄 수정하지 않는다.

### A에서 시그널링 실행

A 저장소 루트의 별도 PowerShell에서 실행한다. 아래 IP를 실제 A 주소로 바꾼다.

```powershell
$env:RA_LISTEN = '192.168.10.10:25001'
$env:RA_VIEWER_DIR = (Resolve-Path 'web/viewer').Path
Push-Location server/signaling
go run .
```

이 터미널은 서버가 실행되는 동안 유지한다. 중단은 Ctrl+C, 이후 `Pop-Location`으로 돌아온다. `RA_ALLOWED_ORIGINS`는 불필요하게 `*`로 설정하지 않는다. Viewer는 같은 서버에서 제공한다.

B에서 확인한다.

```powershell
Test-NetConnection 192.168.10.10 -Port 25001
Invoke-WebRequest -UseBasicParsing http://192.168.10.10:25001/healthz
```

TCP 성공과 `/healthz`의 HTTP 200·본문 `ok`를 확인한다. A 브라우저에서 `http://192.168.10.10:25001/`을 열어 Viewer가 표시되는지도 본다. `file://`로 HTML을 열지 않는다. **B의 localhost는 A가 아니다.** health 성공은 영상 수신 성공이 아니다.

## 6. Codex 원격 실행 준비 — 반복 자동화 시 필요

처음에는 사용자가 B에서 Host를 직접 실행하고 A에서 함께 관찰해도 E2E를 진행할 수 있다. Codex가 B의 빌드·로그 수집·재실행을 반복하려면 아래 관리 경로가 추가로 필요하다.

### OpenSSH 준비

1. A에 OpenSSH Client, B에 OpenSSH Server가 있는지 확인한다. 없으면 Windows 선택적 기능에서 설치한다. 설치에는 관리자 권한이 필요하다. [Microsoft 설치 안내](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_install_firstuse)
2. B의 일반 테스트 계정으로 공개키 인증을 준비한다. 개인키는 A에만 보관하고, B에는 공개키만 등록한다. 관리자 계정은 기본 공개키 파일 위치가 다르므로 일반 계정 구성을 우선한다. [Microsoft 공개키 인증 안내](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement)
3. 새 테스트 전용 SSH 구성은 TCP `25002`를 사용한다. B의 `%ProgramData%\ssh\sshd_config`에서 설정하고 변경 후 `sshd`를 재시작한다. 기존 SSH 사용자가 있다면 먼저 영향과 대체 경로를 확인한다. [Microsoft 서버 설정 안내](https://learn.microsoft.com/en-us/windows-server/administration/OpenSSH/openssh-server-configuration)
4. B의 SSH 인바운드를 A의 IP·신뢰하는 프로필로 제한한다. 설치 시 생성되는 TCP 22 기본 규칙도 확인한다. 이 시험만을 위해 설치했다면 불필요한 기본 노출을 남기지 않되, 기존 운영 규칙은 임의로 삭제하지 않는다.
5. 첫 접속에서 B의 호스트 키 지문을 B 로컬에서 확인한 값과 대조한다. 호스트 키 검사를 끄지 않는다.
6. 키 인증이 되는지 먼저 확인한 뒤 인증 정책을 정한다. 비밀번호·개인키를 채팅, 저장소, 명령 인수에 넣지 않는다. 키 암호가 있다면 실행 계정에서 사용할 수 있는 SSH agent 등으로 준비한다.

아래 `ra-e2e-host`는 A의 SSH 설정에 **사용자가 만들 별칭**이다. 현재 저장소가 제공하는 이름이 아니다. HostName=B 주소, User=테스트 계정, Port=25002, IdentityFile=전용 키 경로를 설정한다.

```powershell
ssh ra-e2e-host hostname
ssh -o BatchMode=yes ra-e2e-host whoami
ssh ra-e2e-host 'powershell.exe -NoProfile -Command "Get-Date -Format o"'
```

실행 결과가 B의 PC 이름·의도한 계정인지 확인한다. 자동화용 `BatchMode=yes` 명령이 추가 암호 입력 없이 성공해야 반복 작업에 사용할 수 있다. 이는 앱 자체의 사용자 동의를 대체하지 않는다.

- [ ] A에서 B의 허용된 작업 디렉터리에 테스트 파일을 전달할 수 있다.
- [ ] B의 테스트 로그를 A로 가져올 수 있다. SFTP/SCP 등 실제 전송 수단을 한 번 검증한다.
- [ ] 접속 계정은 테스트 작업 폴더의 읽기·쓰기·실행 권한만 필요한 범위로 가진다.
- [ ] 원격 셸은 기본값이 cmd일 수 있으므로 PowerShell 명령은 위처럼 명시적으로 호출한다.
- [ ] 허용 작업을 합의한다: 빌드·실행·테스트 프로세스 종료·로그 수집. 재부팅·계정/방화벽 변경·관리자 작업은 별도로 승인한다.
- [ ] Codex 실행 환경에서 SSH·파일 전송 도구 사용과 B로의 네트워크 접근이 실제 허용된다.

### SSH와 화면 캡처 세션은 별개

**SSH에서 HostRun을 시작했다고 B의 로컬 로그인 화면에서 실행됐다고 볼 수 없다.** Windows 세션·데스크톱 경계 때문에 검은 화면이나 다른 세션 캡처로 이어질 수 있다. SYSTEM 서비스 등록으로 해결되는 문제도 아니다.

첫 시험에는 B의 바탕화면에서 사용자가 직접 PowerShell을 열어 HostRun을 실행한다. 이후 자동화에는 다음 조건을 충족하는 실행 수단을 별도로 만든다.

- 로그인된 테스트 사용자의 대화형 세션에서 실행한다. 예약 작업을 사용한다면 **사용자가 로그온할 때만 실행**하는 설정을 사용하고 세션 ID를 검증한다. PowerShell의 `Interactive` logon 유형은 [Microsoft 작업 주체 문서](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/new-scheduledtaskprincipal?view=windowsserver2025-ps)를 참고한다.
- 일반 캡처 검증을 위해 SYSTEM이나 ‘가장 높은 수준의 권한’을 기본으로 사용하지 않는다.
- 실행 파일·작업 폴더·환경 변수·로그 경로를 고정하고, 사용자가 해당 시험 실행을 승인한 뒤에만 시작한다. 자동 로그인·부팅 시 무인 화면 공유를 설정하지 않는다.
- PID와 Windows 세션 ID를 남기고, 지정한 테스트 프로세스만 종료할 수 있게 한다. `dotnet` 프로세스를 전부 종료하는 방식은 사용하지 않는다.
- HostRun의 정상 중단(Ctrl+C), 제한 시간 초과 시 해당 프로세스 정리, 실패 로그 회수까지 검증한다. 예약 작업 실행 요청 성공만으로 Host 시작 성공을 판정하지 않는다.

이 사용자 세션 실행기와 중단 수단은 **현재 제공되지 않는다**. 준비가 안 됐다면 수동 실행으로 범위를 명시하고 진행한다. RDP는 세션·화면·GPU 조건을 바꿀 수 있으므로 첫 LAN 시험 중에는 연결하지 않는다. RDP 공존은 별도 테스트 항목이다.

## 7. Viewer 관찰·자동화 준비

- [ ] A의 전용 브라우저 프로필에서 Viewer와 개발자 도구를 열 수 있다.
- [ ] Console 오류, Network의 WebSocket 메시지, 수신 영상과 통계를 확인할 수 있다.
- [ ] WebRTC 진단 정보에서 선택 candidate pair와 송수신 통계를 회수할 수 있는지 테스트 시 확인한다.
- [ ] 자동화가 필요하면 해당 Codex 세션의 브라우저 제어 도구 또는 별도 테스트 하네스를 준비한다. 현재 저장소에는 준비된 Playwright 테스트가 없다.
- [ ] 브라우저 디버깅 포트를 LAN/인터넷에 노출하지 않는다. 필요하면 로컬 전용으로 제한하고 테스트 프로필만 연결한다.
- [ ] 자동화로 측정할 항목과 직접 눈으로 확인할 항목을 구분한다. video 요소 존재·접속 상태만으로 화면 내용의 정확성을 통과 처리하지 않는다.

화면 캡처 권한은 B의 네이티브 Host가 사용하는 경로다. A 브라우저의 화면 공유 선택 창을 여는 것이 이 앱의 정상 연결 절차는 아니다.

## 8. 준비 완료를 확인하는 최소 실행

이 절차는 사전 smoke test다. 버그가 발견되면 준비 부족과 구현 결함을 분리해 기록하고 [리뷰 태스크](code-review-task-risks-2026-10-07.md)에 연결한다.

1. A에서 5절의 서버를 실행한다.
2. B의 로컬 사용자 PowerShell을 저장소 루트로 이동하고 아래 명령을 실행한다.

   ```powershell
   dotnet run --project tools/RemoteAssist.HostRun -- --signaling http://192.168.10.10:25001 --monitor 0 --fps 30 --bitrate 4000
   ```

3. B에 출력된 새 세션 코드·PIN을 A의 Viewer에 입력한다. 화면 공유 승인 범위를 확인한 참여자끼리 전달한다.
4. B 화면의 식별 문구가 A에 나타나는지 확인한다. B에서 창 이동·스크롤을 하며 실제 영상 갱신을 확인한다.
5. 선택 인코더·해상도·수신 프레임·candidate pair를 기록한다. 첫 프레임 도착과 관찰 구간을 시각으로 남긴다. 30fps/4000kbps 설정값을 실측으로 기록하지 않는다.
6. A에서 종료하고 B에서 Ctrl+C로 HostRun을 중단한다. 프레임 송신과 시험 프로세스가 멈췄는지 확인한다. 정상 종료가 멎으면 해당 PID를 기록하고 합의한 중단 절차로 정리한다.
7. 새 HostRun·새 코드로 한 번 더 시작해 기본 실행을 재현한다. 동일 HostRun의 재접속 복구와는 다른 시험이다.

현재 R07/R08 때문에 오류 후 종료나 동일 인스턴스 재연결이 실패할 수 있다. 프로세스 재시작으로 우회했으면 그 사실을 기록하고 회귀 테스트 통과로 처리하지 않는다. 첫 연결 전에 서버·Host·Viewer 잔여 인스턴스가 있는지도 확인한다.

## 9. 로그·증거·판정 준비

실행별로 고유 ID를 정한다. 예: `20261007-210000-lan-Aviewer-Bhost`. 원본 로그·PNG·브라우저 진단 파일은 저장소 밖의 접근 제한 디렉터리에 보관하는 편이 안전하다. 저장소 내부 `.artifacts/e2e/`를 사용한다면 **각 PC에서** `git check-ignore`로 무시 여부를 확인한다. A의 로컬 제외 설정이 B에도 적용된다고 가정하지 않는다.

| 수집물 | 반드시 남길 내용 |
|---|---|
| 환경 기록 | commit·변경 파일, 각 PC 역할, OS/GPU/드라이버, 브라우저, SDK, FFmpeg 해시 |
| 실행 기록 | 시작·종료 시각/시간대, 명령과 옵션, PID/세션 ID, 사람이 승인한 시험 범위 |
| Host | 모니터·backend·선택 인코더, 전송 프레임, 예외, 종료 결과 |
| 시그널링 | 접속·이탈·오류, 서버 시작 설정, 재시작 여부 |
| Viewer | Console, WebSocket 오류, 영상 캡처, 디코딩/수신 통계 |
| 네트워크 | LAN/별도 NAT/VPN 유무, 선택 candidate pair, 방화벽 변경과 패킷 차단 조건 |
| 판정 | 기대 동작, 실제 동작, 재현 횟수, PASS/FAIL/BLOCKED/NOT IMPLEMENTED |

현재 로그에는 PIN 등이 포함될 수 있다(R15). 세션 코드·PIN·Host 토큰·인증 헤더·개인키는 보고서에서 제외한다. SDP/ICE와 브라우저 진단에도 내부 IP·식별 정보가 들어갈 수 있으므로 공유 전에 검토한다. 원본 로그를 `docs_working/`에 그대로 넣지 않는다. 이 디렉터리에는 비밀정보를 제거한 분석·결과 문서만 둔다.

다음 기준을 시험 전에 합의한다.

- 연결 대기 제한, 관찰 시간, 반복 횟수, 허용할 프레임 정지·종료 시간. 정하지 않은 성능 목표를 사후에 통과 기준으로 만들지 않는다.
- 영상 정상 판정은 올바른 PC·모니터·방향·크기·내용 갱신까지 포함한다.
- 브라우저 통계의 RTT는 화면 캡처부터 표시까지의 end-to-end 지연이 아니다. 지연 측정은 측정 위치·시계 오차·방법을 따로 기록한다.
- `BLOCKED`는 환경 때문에 실행하지 못한 것, `NOT IMPLEMENTED`는 기능 자체가 없는 것이다. 둘 다 PASS가 아니다.
- 관측 없는 성능 수치는 추정해서 넣지 않는다. 한 GPU나 두 PC의 성공을 전체 지원 환경의 보증으로 확대하지 않는다.

## 10. 기본 시험 이후 준비할 환경

| 확대 시험 | 추가 준비 | 현재 판정 범위 |
|---|---|---|
| 역할 교환 | A에도 .NET/FFmpeg 준비, B에도 Viewer 준비 | GPU·Host 환경 차이 확인 |
| 해상도·회전·다중 모니터 | 두 번째 모니터, 설정 원복 기록 | R02~R04 검증. 정적 정상 경로와 분리 |
| 일시 단절·서버 종료 | 현장 복구 담당자, 테스트 프로세스 식별 | SSH도 끊길 수 있으므로 원격 복구만 믿지 않는다 |
| 다른 NAT | 한 PC의 핫스팟 등 별도 회선, 양쪽이 도달 가능한 안전한 시그널링 경로 | 핫스팟만 켜면 A의 사설 주소에 접근할 수 없게 될 수 있다 |
| TURN 강제 | 앱 TURN 설정/자격증명/강제 relay 지원, 인증된 TURN 서버, UDP·TCP/TLS 정책 | 현재 미구현. 양쪽의 실제 선택 pair로 relay 사용을 증명 |
| UAC·잠금·SAS | 기능 구현, 별도 관리자 동의, 현장 조작자·복구 계정 | 현재 미구현. 보안 데스크톱·UAC 비활성화로 통과시키지 않는다 |
| 파일·클립보드·입력 | 기능 구현, 합성 데이터·임시 폴더, 철회/거부 시나리오 | 실제 개인 파일이나 업무 앱으로 시작하지 않는다 |

별도 NAT 시험에서 사설 VPN으로 A/B를 연결하면 테스트 경로 자체가 달라진다. 관리용 연결과 미디어 경로를 구분하고 실제 candidate pair를 기록해야 한다. 직접 연결을 차단했다는 이유만으로 TURN 경유를 추정하지 않는다. 현재 보안 조건을 충족하지 못한 PoC 서버를 인터넷에 공개하는 방식은 사용하지 않는다.

## 11. 테스트 종료·원복 준비

- [ ] Host·시그널링·테스트 브라우저를 종료하고 잔여 테스트 프로세스·listener를 확인한다.
- [ ] 이번 시험용으로 추가한 방화벽 규칙·예약 작업·SSH 접근을 유지할지 결정하고, 불필요한 것만 제거하거나 비활성화한다. 기존 운영 설정은 건드리지 않는다.
- [ ] 임시 계정·키·원격 접근 권한을 더 쓰지 않으면 회수한다.
- [ ] 절전·잠금·해상도·모니터·네트워크 설정을 원래 상태로 되돌린다.
- [ ] 원본 로그·화면 파일의 보관 기한과 접근자를 정하고, 보고서에는 비밀정보를 제거한 결과만 남긴다.

## 12. 최종 체크리스트와 테스트 요청 양식

### 첫 수동 LAN E2E를 시작할 수 있는 조건

- [ ] A/B 역할·주소·저장소 경로·동일 commit을 확인했다.
- [ ] A의 Go 빌드·테스트와 B의 C# 빌드가 성공했거나, 실패 내역을 공유했다.
- [ ] B의 FFmpeg DLL과 실제 캡처·인코더 출력 검사를 완료했다.
- [ ] B는 테스트 계정으로 로컬 로그인했고, 비민감 화면과 물리적 중단 수단이 있다.
- [ ] B에서 A의 TCP 25001과 `/healthz`에 접근하고 A에서 Viewer가 열린다.
- [ ] 미디어 통신의 방화벽 조건과 현재 포트 정책 제약을 확인했다.
- [ ] 로그·스크린샷 보관 위치, 비밀정보 처리, 승인 범위를 정했다.

### Codex가 반복 실행할 수 있는 추가 조건

- [ ] A에서 B의 SSH 명령 실행과 파일 왕복 전송을 확인했다.
- [ ] Codex 실행 환경에서도 같은 접근이 허용된다.
- [ ] Host를 올바른 사용자 세션에 실행하고 특정 프로세스만 중단하는 수단이 있다. 없다면 사람이 실행·중단을 담당한다.
- [ ] A의 Viewer를 관찰·제어할 브라우저 도구 또는 하네스를 준비했다. 없다면 수동 검증 범위를 명시한다.
- [ ] 네트워크 단절·UAC·잠금 등 사람이 개입할 항목과 가능한 시간을 정했다.

나중에 테스트를 요청할 때 아래 양식을 채워 전달하면 된다. 비밀번호·개인키·실제 세션 PIN은 넣지 않는다.

```text
테스트 commit / 미커밋 변경:
A 역할 / LAN 주소 / 저장소 경로:
B 역할 / LAN 주소 / 저장소 경로:
B OS·GPU·드라이버 / 모니터·해상도·DPI:
연결 환경: 동일 LAN / 별도 NAT / VPN 유무
SSH 별칭 / 포트 / 접속 계정 / 연결 확인 여부:
파일 전달·로그 회수 방법:
Host 사용자 세션 실행·중단 방법: 직접 실행 / 검증한 실행기
Viewer 브라우저·버전 / 자동화 도구 연결 여부:
빌드·CaptureDump·encoder-check 결과:
로그 저장 위치 / 보관 기한:
허용 작업과 관리자 작업 승인 범위:
물리적으로 PC를 조작할 수 있는 시간:
이번에 검증할 범위 / 제한 시간 / 반복 횟수:
```

최소 준비는 **두 PC + 신뢰하는 LAN + B의 로컬 로그인·FFmpeg + A의 시그널링·Viewer + 로그 수집**이다. 여기에 **SSH·사용자 세션 실행기·브라우저 자동화**를 연결하면 반복 가능한 자동 E2E 환경으로 확장할 수 있다.
