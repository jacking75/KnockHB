## 0. 이 문서의 역할과 현재 위치

이 문서는 **프로젝트의 단일 구현 계획**이다. 기존 Phase/T 로드맵과 최종 E2E 전 상세 계획을 통합했다. 별도의 구현 계획 문서를 병행 관리하지 않는다.

- **T0.1~T6.4:** 기존 기능 묶음의 식별자다. 8장의 대응표에서 목표·E/V/F 연결을 찾는다. 별도 완료 체크리스트를 중복 유지하지 않는다.
- **E01~E41:** 구현·코드 리뷰 태스크다. **진행 상태는 3장의 E 체크리스트가 기준**이다.
- **V01~V41:** E 전체 완료 뒤 실행하는 별도 검증 태스크다. 각 V는 같은 번호의 E를 검증하며 **진행 상태는 9.1장의 V 체크리스트가 기준**이다.
- **F01~F12:** 구현 후 두 PC에서 수행할 최종 E2E다. **진행 상태는 10장의 F 체크리스트가 기준**이다.
- **R01~R18/G01~G06:** [리뷰 문서](code-review-task-risks-2026-10-07.md)의 결함·설계 위험 ID다. 상세 근거는 리뷰에 두고 구현 작업은 E에 연결한다.
- 과거 PoC 검증·수정 이력은 **12장**에 보존한다. 당시 실행 성공 기록을 현재 V/F의 완료 체크로 자동 승계하지 않는다.

현재 제품 경로는 SYSTEM 서비스→일반 WPF Tray/Helper→웹 Viewer이며 일반/관리자 입력·독립 키 복원·파일/채팅/클립보드/진단/등록 Runbook·모니터/적응 품질·TURN 새 transport 세대·감사 보고·서명 설치/업데이트/rollback을 연결했다. 기존 실증은 과거 근거로 보존하고 새 후보의 실행 검증으로 자동 승계하지 않는다.

### 현재 진행 요약 — 구현/리뷰와 검증 분리

E는 구현·코드 리뷰, V는 실행 검증, F는 실제 두 PC 최종 E2E다. 이번 요청은 E02~E41 전체 구현 뒤 main push다. E 단계에 실행 검증을 끼워 넣지 않고 검사 코드/준비/판정/정리를 작성·리뷰한다. Gate I 뒤에 비대화형 검사를 실행하며 실제 화면·서비스·UAC·TURN·설치/부하 실증은 준비된 V/F 묶음으로 별도 수행한다.

- f440dfc 전달 당시 E01~E41 구현/리뷰와 비대화형 검사를 마쳤다. 이후 30분 제한의 보수적 재리뷰에서 하네스의 전역 deadline/정리 준비 부족을 발견해 E39/E41을 다시 열었다. 현재 Gate I 재마감과 E2E 준비 완료는 미충족이다.
- V의 자동 검사 일부를 실행했다. 각 V의 전체 실증/수용 조건을 충족한 것은 아니므로 V01~V41은 모두 미체크로 남긴다. 결과와 미실행 조건은 9.1장의 실행 증거에 구분한다.
- F01~F12는 모두 미실행이며 사용자 별도 수행이다.

기존 파일 채널 교착/timeout은 bounded 비동기 transport fixture와 취소 소유권으로 수정했고 건별 UI/감사 ACK·양방향 채널을 연결했다. 제품 경로와 거부/철회/늦은 세대·native hang 감독을 리뷰했다. 실제 빌드·시험·브라우저·서명 설치 성공은 이 문단으로 주장하지 않는다.

정식 Authenticode 인증서/TrustedPublisher·업데이트 HTTPS endpoint/운영 키·공개 대응 소스·TURN/TLS 서버/실제 allocation·깨끗한 VM·다른 로그인 계정/다른 GPU/두 물리 PC·현장 UAC/잠금 조작자는 외부 실행 자원이다. V/F의 BLOCKED와 E 구현 누락을 구분한다. 기업 HA/RBAC·무인 접속·임의 셸·AI 자동 조치는 원래 1차 범위 밖이다.

### 기존 실증과 현재 후보

과거 일반 화면·입력·즉시 종료·일부 crash/up 복원·일반/SYSTEM UAC/잠금 최소 실증은 [실행 증거](implementation-evidence-2026-10-08.md)에 보존한다. 당시 실패/미실행과 값은 당시 후보의 결과다. 현재 구현 상태와 실행 수용은 이 문서만 기준으로 삼는다.

후보는 새 commit과 .NET/Go/Viewer/설정/FFmpeg의 파일 SHA256으로 고정한다. 로컬 검증 runner는 dirty 여부/명령/시간/deadline/exit/output을 기록하고 제품 하네스는 준비·실제 기능 관찰·중단/정리를 분리한다. main push 뒤 로컬/원격 HEAD와 clean tree를 확인한다. V/F/Gate A/B를 모두 통과하기 전에는 정식 출시/운영 수용을 선언하지 않는다.

### 유지하는 기술 결정

Host는 C#/.NET 10, 서비스 감독과 WPF 사용자 UI를 분리한다. 시그널링은 Go, Viewer는 정적 바닐라 JS, TURN은 coturn이다. C#은 Windows API 통합, Go는 WebSocket 동시성과 독립 배포를 기준으로 선택했다.

캡처는 WGC 기본/DXGI 폴백, 인코딩은 `SIPSorceryMedia.FFmpeg` H.264다. FFmpeg 8.1 ABI의 프로젝트 허용 LGPL shared 빌드를 별도 DLL로 동봉한다. 인코더 후보 순서는 `h264_nvenc → h264_qsv → h264_amf → h264_mf → libopenh264`이며 `libx264`와 deprecated `SIPSorceryMedia.Encoders`는 사용하지 않는다. `IVideoEncoder` 추상화는 유지하고 Media Foundation 직접 구현은 필요 시 재검토할 대안이지 현재 별도 필수 구현이 아니다.

기술 세부와 실제 선언 버전은 [기술 사양](../docs/technical-specification.md), [스택 기록](../docs/stack.md), [중앙 패키지](../Directory.Packages.props), [Go 모듈](../server/signaling/go.mod)이 기준이다. 코드 구조·API 스켈레톤은 여기에서 중복 유지하지 않는다. 하드웨어별 지원·배포 라이선스와 특허 검토는 확인 증거 없이 완료로 선언하지 않는다.

## 1. 목적과 범위

## 2. 완료의 의미와 실행 순서

### 단계와 게이트

1. **E01~E41 — 구현·코드 리뷰:** 기능·오류/거부/철회/취소/timeout·자원 소유권·UI·계약·문서·검사 코드/하네스를 작성하고 리뷰한다. 각 E의 기능 범위가 코드에 연결되고 알려진 해당 결함을 수정하면 즉시 체크한다. 실행 검증이 대기 중이라는 이유만으로 E를 미체크로 남기지 않는다.
2. **Gate I — 구현·코드 리뷰 완료:** 모든 E가 완료됐고 남은 것은 실행 검증이다. 코드 리뷰가 해결하지 못한 명확한 결함이나 빠진 기능은 V로 넘기지 않는다. Gate I는 빌드 성공·기능 동작·성능·배포 승인을 뜻하지 않는다.
3. **V01~V41 — 구현 전체 완료 후 검증:** 후보를 고정하고 빌드·의존성/배포 검사·단위/계약/통합·Windows/브라우저 실증·relay·설치/업데이트·보안/장애/부하를 실행한다. 전제 조건과 준비는 E39/E40/E41에서 작성·리뷰하고 실행은 이 단계에서만 한다.
4. **Gate A — 최종 E2E 착수 가능:** E와 필수 V가 완료되고 검증된 후보·환경·증거가 준비됐다. 외부 자원 부재는 해당 V/F의 BLOCKED로 표시하고 정식 서명/배포 가능성을 주장하지 않는다.
5. **F01~F12 / Gate B — 실제 두 PC 최종 E2E:** 사용자가 별도로 수행한다. 모든 필수 시나리오가 통과한 경우에만 최종 E2E 완료로 판정한다.

**고정 실행 순서는 E 전체 구현 → 코드 리뷰 마감/Gate I → V 실행 검증/Gate A → F 별도 최종 E2E다.** E의 직접 선행은 구현 의존성이다. 앞 E의 실행 시험 통과를 후속 구현의 시작 조건으로 두지 않는다. 검사 코드 작성은 구현이며, 빌드/검사/실증 실행은 검증이다. 구현에 필요한 라이브러리/API 계약 확인·코드 읽기·문서 정합성 확인은 코드 리뷰에 포함한다. 사용자 명시 요청 전 CI는 생성·수정·실행·진단하지 않는다.

### E의 공통 완료 조건

- 계약·와이어·기능 범위를 먼저 확정하고 제품 실행 경로·권한 게이트·UI·오류 안내·문서를 연결했다.
- 정상 경로와 거부·철회·취소·timeout·늦은 callback·프로세스 종료의 코드 경로를 리뷰했다. 최소 권한·세션/세대·입력/자원 소유권·동시성·유한 큐·민감정보 경계를 확인했다.
- 필요한 자동 검사 케이스·fake/barrier·준비/실행/판정/정리 절차를 작성·리뷰했다. 실행 통과는 요구하지 않고 해당 V에 추적한다.
- 리뷰 범위/근거 파일·관련 R/G·남은 V를 기록했다. 해당 기능의 알려진 결함과 빠진 연결은 해결했다. TODO·비활성 placeholder·mock만으로 제품 기능을 완료 체크하지 않는다.
- 성능 목표·실측 결과, 구현 상태·검증 상태를 구분한다. E 체크를 OS/GPU 지원·정식 서명·설치 성공·릴리스 검증으로 표현하지 않는다.

### V/F 실행 준비와 시간 제한

**E2E와 단일 PC 제품 실증은 충분한 계획·준비·사전 리뷰를 마친 뒤에만 실행한다. 준비되지 않은 시험을 반복하며 환경을 맞추는 방식을 금지한다.** 개발 시간을 검증 시행착오에 소비하지 않고 사용자 화면 점유를 최소화하는 필수 실행 규칙이다. 계획/준비는 E39/E40/E41에서 작성·리뷰하며 실제 사전 점검과 실행은 E 전체 완료 후 V/F에서 수행한다.

실행 전 [E2E 준비표](e2e-test-preparation.md#required-execution-plan)에 다음을 빠짐없이 확정한다.

1. **범위와 판정:** 대응 V/F·확인할 기능/결함·단계별 기대 상태·관찰 가능한 PASS/FAIL·필요 증거·재사용/생략할 검사다. 한 묶음에 준비된 시나리오만 넣고 실행 중 범위를 넓히지 않는다.
2. **후보와 환경:** commit/hash·설정·도구/모듈·사용자/Session/desktop·인증서/포트·현장 조작자·대상 창/모니터/물리 좌표·소유 PID/이미지 경로다. 준비용 명령과 수집/정리 코드를 리뷰하고 입력을 주입하지 않는 사전 점검으로 확인한다.
3. **순서와 준비 신호:** 연결·동의·영상/채널·snapshot/foreground·입력/키 상태의 준비 완료 조건, 단계별 명령·기대 결과·실패 분기다. 고정 sleep·추측 좌표·fault 시점의 PID 탐색으로 대체하지 않는다. 같은 머신의 Viewer 포커스/reset 간섭과 UAC/잠금 후 복귀를 미리 고려한다.
4. **시간과 중단:** 시나리오별/전체 숫자 상한과 중단 조건이다. 화면 점유 묶음은 기본 5분 이내로 설계한다. 빌드·게시·설치 준비·원인 분석은 점유 구간 밖에 둔다. 긴 성능/부하 검사는 화면 점유 없는 별도 묶음으로 계획한다. 실행 직전 목적·점유 예상 시간·중단 조건을 사용자에게 짧게 알린다.
5. **수집과 복구:** 실행 ID·타임라인·관찰/로그·실패 직전 상태·입력 해제·세션 종료·소유 창/브라우저/서비스/배치 정리·일반 작업 복귀 확인이다. 정리 실패는 다음 시험보다 먼저 해결한다. 대상자 동의를 자동 승인하거나 보안 경계를 약화해 준비 문제를 회피하지 않는다.

준비표의 미확정/실패 항목이 있으면 실행하지 않는다. 실패·신호 누락·상한 초과 시 첫 실패 지점에서 중단하고 정리한다. 화면을 점유한 채 코드 수정·환경 탐색·다른 시험을 이어가지 않는다. 수집한 증거로 원인을 좁히고 수정/준비 변경·예상 결과·판정/정리를 리뷰한 뒤 영향받은 시나리오만 재실행한다. **원인과 준비가 바뀌지 않은 동일 시험의 반복은 금지한다.** 각 묶음의 실제 점유 시간·확인한 결과/새 결함·정리 결과를 기록하며, 시간에 비해 결과가 적으면 다음 실행 전에 계획과 관측 수단을 개선한다.

기존 증거의 후보/변경 범위가 일치하면 재사용 가능 여부를 먼저 검토해 불필요한 재시험을 줄인다. 실행하지 않은 검사는 PASS로 처리하지 않는다.

**최신 기준은 전체 회차 목표600초·절대 상한900초다.** 중단·정리·외부 복귀·결과 전달까지 포함한다. 종전30분 기준과 아래22분 기능 시간표, campaign-plan.json version1의1800초 예산은 폐기된 검토 자료다. 현재 실행 가능한15분 시간표나 runtime guard가 완성됐다는 뜻이 아니다. ### E10 — Viewer 연결 객체·ICE 큐·오류 보존

- **수정 위치:** `web/viewer/app.js` 및 분리 모듈. 연결: R06/R09/R16.

## 6. TURN·보조 기능·품질

### E27 — coturn 배포와 네트워크 정책

- **수정 위치:** `deploy/coturn`, 운영 설정 예시, 배포 문서. 연결: T4.1/T4.2, G04.
- **구현 방법:** 이미지 버전/digest를 고정하고 개발 고정 비밀번호를 제거한다. 인증·realm·외부 주소/NAT 매핑·relay 포트·quota·인증서·접근 제한을 설정한다. loopback/내부 민감 목적지로의 릴레이 악용을 제한한다. Windows Docker의 host networking을 Linux와 동일하다고 가정하지 않는다.

### E28 — 세션별 단기 TURN 자격증명

- **수정 위치:** Go credential 발급, Host/Viewer ICE 설정 수신. 연결: T4.2.
- **구현 방법:** 인증된 세션 참가자에게만 제한 시간의 username/credential/urls를 제공한다. 공유 secret은 서버에만 두고 secret rotation·시계 오차·유효시간·장시간 세션 갱신을 설계한다. 익명 endpoint로 무제한 발급하지 않는다.
- **철회:** 자격증명 만료가 기존 allocation을 즉시 제거한다고 가정하지 않는다. 앱 송신 차단과 TURN quota/만료/관리 측 정리를 구분해 종료 정책을 만든다. 로그·브라우저 영구 저장소에 비밀을 남기지 않는다.
- **구현·리뷰 완료 조건:** 세션별 HMAC TURN 자격증명·만료·재발급/갱신·키 교체·권한/빈도 제한을 구현하고 리뷰했다.
- **별도 실행 검증:** [V28](#validation-v28)에서 기존 실행/수용 조건을 확인한다. E 체크에는 실행 통과를 요구하지 않는다.

### E29 — ICE 통합·relay 강제·연결 복구

- **수정 위치:** Host/Viewer PeerConnection, signaling 협상 세대, 경로 UI. 연결: T4.1~T4.3, R06/R08, G04.
- **구현 방법:** 양쪽에 STUN/TURN URL·자격증명을 제공하고 자동/relay 전용 시험 모드를 둔다. 고정 SIPSorcery의 relay 정책·ICE restart 지원을 먼저 확인해 미지원 시 검증 가능한 adapter나 PeerConnection 재생성 정책을 구현한다. 브라우저의 relay 정책은 [W3C WebRTC 규약](https://www.w3.org/TR/webrtc/)과 맞춘다.
- **복구:** 시그널링은 정상이고 ICE만 일시 disconnected일 때 제한된 backoff/timeout으로 재협상한다. 기존 코드/PIN 재사용이 아니라 동일 승인 주체·세대에 묶인 복구다. 권한 철회·시그널링 상실·피어 변경 뒤 자동 재개는 금지한다.
- **경로:** 실제 선택된 candidate pair의 local/remote 양쪽을 보고 한쪽이라도 relay면 Relay로 표시한다. 후보 수집 성공을 relay 사용 성공으로 표시하지 않는다. 브라우저의 동적 미디어 포트 제어 가능성과 프로젝트 대역 정책의 제약을 실증하고 문서화한다. 미해결 구현 정책은 E29에서 해소하고, 실제 포트/경로 조건 실패는 V29/Gate A 차단이다.
- **구현·리뷰 완료 조건:** 양쪽 ICE 설정·relay 강제·선택 pair 표시·세대별 복구/재협상·timeout 종료·동의 유지 정책을 구현하고 리뷰했다.
- **별도 실행 검증:** [V29](#validation-v29)에서 기존 실행/수용 조건을 확인한다. E 체크에는 실행 통과를 요구하지 않는다.

- **구현 방법:** CPU/메모리/디스크/네트워크/오류 이벤트/시작프로그램/서비스 상태의 최소 필드를 정의한다. E04에서 control 또는 별도 telemetry 채널을 확정해 기존 chat/control 초안 불일치를 해소한다. 수집 주기·크기·동시 요청·timeout을 제한한다.
- **권한:** 진단 자체에 별도 동의를 요구한다. 기본은 일반 권한 읽기이고 접근 불가 정보는 N/A로 표시한다. 서비스 상태 조회가 서비스 시작/중지 권한으로 확장되지 않게 한다. 이벤트 메시지의 개인정보와 경로는 최소화한다.
- **구현·리뷰 완료 조건:** 일반 권한 읽기 전용 provider·수집 동의·영상 없는 세션·제한/timeout/취소·N/A/stale·Viewer 대시보드를 구현하고 리뷰했다.
- **별도 실행 검증:** [V33](#validation-v33)에서 기존 실행/수용 조건을 확인한다. E 체크에는 실행 통과를 요구하지 않는다.

### E34 — 승인형 Runbook

- **수정 위치:** 서명/고정 hash의 Runbook manifest, 별도 실행 worker, Viewer/Tray 승인·결과 UI. 연결: T5.7.
- **구현 방법:** 서버가 보낸 임의 스크립트 대신 설치·승인된 allowlist의 ID/version/hash와 형식 검증한 인자만 실행한다. 실제 본문·변경 영향·권한을 미리 보여주고 실행 건별 승인을 해당 hash/인자/세션에 묶는다. 승인 후 내용 변경은 재승인한다.
- **격리:** 읽기 전용을 기본으로 하고 변경형·관리자형은 별도 권한/승인을 요구한다. 쉘 문자열 이어붙이기를 금지하고 인자를 분리한다. 실행 시간·출력 크기·자식 프로세스·취소를 제한하고 stdout/stderr/exit code를 수집한다. PowerShell 실행 자체가 보안 sandbox라고 가정하지 않는다.
- **구현·리뷰 완료 조건:** 설치된 ID/version/hash allowlist·인자 제한·영향 미리보기·건별 승인·worker/권한·timeout/취소·출력 제한·감사를 구현하고 리뷰했다.
- **별도 실행 검증:** [V34](#validation-v34)에서 기존 실행/수용 조건을 확인한다. E 체크에는 실행 통과를 요구하지 않는다.

### E35 — 적응형 품질과 배압

- **수정 위치:** stats 수집, 품질 controller, 인코더 재설정, Viewer 품질 UI. 연결: T6.3, G04/G05.
- **구현 방법:** 실제 packet loss/RTT/송수신 bitrate/encode·decode 시간에 따라 상하한·hysteresis·최소 유지 시간을 가진 품질 정책을 적용한다. bitrate/FPS/해상도 변경은 E12 포맷 트랜잭션과 E11 키프레임을 거친다.
- **우선순위:** 오래된 영상 frame을 bounded queue에서 버리고 제어·입력·철회를 보호한다. 파일 전송은 자체 throttle을 적용하되 별도 데이터채널이라고 네트워크 경합이 사라진다고 가정하지 않는다. WGC에 없는 dirty rect를 전제한 최적화는 제외한다.
- **구현·리뷰 완료 조건:** 유한 큐/제어 우선·통계·적응 품질 정책/상하한·안정화·성능 개선·설정/실측 표시를 구현하고 리뷰했다. 수치달성은 V35에서 판정한다.

### E36 — 설치·서명·업그레이드·제거

## 9. 구현 완료 뒤 실행 검증과 Gate A

### 9.1 V01~V41 — 별도 실행 검증 태스크

**모든 V의 공통 선행은 Gate I(E01~E41 전체 구현·코드 리뷰 완료)다.** 아래는 각 E에서 분리한 기존 실행/수용 조건이며 기준을 삭제하거나 낮추지 않는다. 기존 통과 기록은 후보/영향 범위를 검토할 참고 증거다. 이번 후속 검증은 모두 미실행으로 시작한다. 각 항목은 후보 commit/hash·명령·결과·환경·측정·남은 F를 기록한 뒤 체크한다. 파일 채널 교착/timeout 수정은 V31에서 현재 후보로 회귀 확인한다.

실행 묶음은 **후보 고정·검증 전제 확인(V41 준비) → 빌드/정적 산출물/단위·계약·비대화형 검사 → 하네스 사전 점검(V39 준비) → 로컬 TURN/설치/업데이트 → 짧은 화면·입력·UAC/잠금·보조 기능 묶음(V39 rehearsal 포함) → 종합 결과(V40) → Gate A 판정(V41)**이다. V41 준비를 먼저 해도 완료 체크는 마지막 판정 뒤에만 한다. 공유하는 검사는 한 번 실행해 여러 V의 증거로 연결하며 기능별로 같은 전체 시험을 반복하지 않는다. 검사 대상·시간 제한·정리 준비가 부족하면 대화형 시험을 시작하지 않는다.

## 11. 구현·리뷰 / 실행 검증 기록 양식

E는 변경 범위·코드 리뷰 근거와 후속 V만 기록하고, 실행 명령/결과는 V/F에 기록한다. 실제 근거는 각 태스크 또는 docs_working 결과 문서에 두어 링크하며 진행 상태는 이 문서만 관리한다.

~~~text
E ID / 구현·리뷰 상태:
변경 commit / 파일 / 계약 / 관련 T-R-G:
코드 리뷰 범위 / 발견 사항 / 수정 근거:
남은 구현 결함 / 대응 V:
~~~

~~~text
V/F ID / NOT RUN-PASS-FAIL-BLOCKED:
후보 commit/hash / 환경 / 전제 조건:
명령 / 실제 결과 / 시간·자원 실측 / 증거:
거부·철회·장애 / 시간 제한 / 정리 결과:
새 결함 / 다시 연 E / 남은 V-F:
Gate I / Gate A / Gate B 판정:
~~~

Gate I 이후 V의 실제 결과를 기록한다. 새 구현 결함을 발견하면 해당 E를 다시 열고 수정/리뷰하며 영향받은 V만 재실행한다. 준비/원인이 바뀌지 않은 대화형 시험을 반복하지 않는다.
